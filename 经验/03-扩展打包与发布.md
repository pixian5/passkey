# 扩展打包与发布

> 适用范围：`apps/extension_shared`（源码）、`apps/extension_chrome_web`（正式 Chrome 产物）、Firefox / Safari 壳层、版本戳与调试。

## 1. 「Receiving end does not exist」九成不是代码问题

**现象**：网页内红色提示条 `Could not establish connection. Receiving end does not exist.`，账号选择/保存浮窗都不出现。
**根因**：Chrome 里加载的扩展是**旧注册**——磁盘文件已更新但没点「重新加载」，MV3 Service Worker 变为无效（`chrome://extensions` 卡片显示 `Service Worker (无效)`），`chrome.runtime.sendMessage` 无接收端；content script 又把 `lastError.message` 英文原文直接弹成 toast。
**正确做法（按顺序排查，不要先改代码）**：
1. 看 `chrome://extensions` → Pass 卡片「检查视图」是否 `Service Worker (无效)`；是 → 点「重新加载」→ 刷新页面，结束。
2. 卡片正常 → 页面是否是重载前打开的（旧 content script 不会重新注入）→ 刷新页面。
3. 两者都排除 → 才查 `runtimeSendMessage` / background 监听。
**出处**：`docs/20261012-2058-Chrome扩展后台无接收端报错根因与修复-Step-5-Preview.md`

## 2. 改共享源码后的固定重建链

```bash
cd apps/extension_shared
npm test
npm run build            # 生成 apps/extension_shared/dist（临时目录，不提交）
cd ../..
./scripts/build-extension-chrome-web.sh   # 刷新 apps/extension_chrome_web/dist（已跟踪，需提交）
```

- Chrome 正式扩展加载 `apps/extension_chrome_web`；只改源码不跑这两步，用户加载到的还是旧产物。
- 源与 dist 必须成对提交；否则会出现「仓库源码已修、dist 仍旧」的假象。
- 重建后仍要在 `chrome://extensions` 重新加载扩展，并**硬刷新已打开页面**（content script 不会随扩展重载更新）。
**出处**：`docs/browser-extension-in-page-prompts-zh.md` §2、根 `README.md`「版本与构建」

## 3. 版本戳必须进 dist，且顺序是 bump → build

**现象**：管理页标题显示 v1.9.0，但实际已含 1.9.1 修复，无法用标题判断跑的是哪份代码。
**根因**：构建先于 bump 执行，dist 里烙的是旧版本；而 `version.mjs` 当时不校验 dist 内的 `PASS_EXTENSION_VERSION` 与 `app_version.js`。
**正确做法**：
- 改代码 → `node scripts/version.mjs bump` → 再 `npm run build` + `build-extension-chrome-web.sh`；
- 版本戳来源纳入 `scripts/version.mjs` 的 bump + check（当前 72 处，含 Chrome dist 5 个 bundle、`app_version.js`、README 当前进度）；
- `scripts/version.mjs check` 必须显示条目数，条目数变化本身是信号。
**出处**：`docs/20261013-1305-…-Hy3.md` §3、`docs/20261013-0021-版本与日志埋点补齐扩展与客户端-Step-5-Preview.md`

## 4. 调试先看版本，不要靠猜

- 每个上下文启动各打一行带版本日志：`[Pass vX] background ready` / `popup ready` / `options ready`。
- 控制台一行查注入版本：
  ```js
  document.documentElement.getAttribute("data-pass-injected-version"); // MAIN world
  document.documentElement.getAttribute("data-pass-content-version");  // isolated world
  ```
- 页面版本与后台不一致时应主动告警并提示硬刷新。**重载扩展只重建 Service Worker，不更新 content script**，这是「注册能过、获取却失败」类问题的常见根源。
**出处**：`docs/20261013-0021-…-Step-5-Preview.md` §1–3

## 5. 网页内浮窗的交互红线

- 宿主用 closed Shadow DOM + `popover="manual"`/`showPopover()` 进 top layer，不支持时回退 `position: fixed`；关键定位样式带 `!important`，不继承站点 CSS。
- 同一页面并行多版本时按三段版本号决定 UI 所有权；已打开的确认框归发起提交的内容脚本处理，不能假定新版本接管。
- 一次点击会同时触发 `pointerdown/focusin/click`，用「输入框对象 + 650ms 窗口」认领一次激活，避免重复请求与多浮窗。
- 保存/更新确认框**没有自动消失计时器**；只有后台 800ms 完全无响应才放行原始提交；一旦浮窗已显示，800ms 兜底不再生效。
- 按钮拒绝 `isTrusted === false` 的合成点击；列表/浮窗/toast/日志/测试断言都不得出现密码正文。
- 恢复表单提交前确认表单仍是 `HTMLFormElement` 且 `isConnected`、提交按钮 `submitter.form === form`，否则放弃，避免 Chrome 的「form is not connected」报错。
**出处**：`docs/browser-extension-in-page-prompts-zh.md` §3–7

## 6. Safari 壳层的三个具体坑

1. **最低系统版本**：调试/发布配置曾覆盖最低系统为 `10.14`，Xcode 27 只接受 `12.0+`，无签名构建直接失败。删掉覆盖，继承项目配置（26.3）即可。
2. **空的 `content_scripts` 数组**会触发「空白或无效的 content_scripts 清单条目」；不需要内容脚本时**删除该字段**，不要留 `[]`。
3. **临时扩展实测 ≠ 原团队签名安装**：`--unsigned` 只能做编译验证；`build_signed_safari.sh` 会先检查钥匙串里是否有该团队的 `Apple Development` 证书与私钥（本项目 macOS 的 `PSTNW3UN4R`），缺失必须停下，不能用临时测试结果宣称正式安装通过。
**出处**：`docs/20261008-1926-Safari扩展实测与发布收尾-GPT-6.md`、`docs/test-baseline-and-sync-e2e-zh.md` §5

## 7. 自动化卡在原生 `window.confirm` 时不要硬刚

**现象**：合并流程的主同步源变更确认用 `window.confirm`；Chrome 原生弹窗不暴露给 System Events，Enter/Esc/空格都打不到，`execute javascript` 超时 `-1712`。
**根因**：AppleScript `execute javascript` 跑在扩展页面的 ISOLATED world，没有 `chrome.runtime`/`chrome.storage`，不 await promise；`chrome.scripting`/`chrome.tabs` 在扩展自身页面也不可用，无法注入主世界绕过。
**正确做法**：这类一次性确认只能由用户手动点；若要自动化，需产品层把该确认改为非阻塞提示或对编程调用自动放行（未改）。
**出处**：`docs/20261013-0349-…-Step-5-Preview.md` §5

## 8. Chrome 多配置文件 = 多个同名进程

AppleScript 的 "Google Chrome" 可能连到非主配置文件的进程，表现为「通过 AppleScript 执行 JavaScript 的功能已关闭」——那是**另一个配置文件**的 per-profile 偏好，不是主窗口被关。用 System Events `get name of every window` 确认当前窗口；窗口 ID 超过 2^31 时不要用大整数定位，用序号。
**出处**：`docs/20261012-2115-…-Step-5-Preview.md`「排障过程记录」

## 9. Firefox / Safari 共用同一份共享产物

Firefox/Safari 壳层复用 `apps/extension_shared` 构建结果，但**不会自动同步**：改了共享层要重新走各自 build 脚本（如 `build-extension-firefox.sh`）才能生效；未打包 XPI 时不要宣称 Firefox 已更新。
**出处**：`docs/20261013-0935-…-Step-5-Preview.md` §8
