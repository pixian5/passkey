# 合并永久墓碑 163 报错诊断增强（1.8.6）

> 涉及版本：pass 1.8.5（增强前的盲报）→ 诊断增强随 1.8.6 发布
> 关联文档：`docs/20261013-0935-固定文件夹墓碑复活触发永久删除护栏拦截缺陷修复-Step-5-Preview.md`（E/F/G/H 节）
> 状态：**根因尚未坐实，等待用户下一次现场报错**

## 1. 现象

用户在 1.8.5 下点「合并」仍被 `PERMANENT_TOMBSTONES_DROPPED` 拦截，报错：

```
同步失败:Error:自建服务器[SAFETY_BLOCKED]:同步安全检查未通过:
PERMANENT_TOMBSTONES_DROPPED[accounts=163(0071f570e-7761-cc42-140e-ccd765e8daae,001f9b07-fa77-41dc-ae6c-2be5b3edcf72,020c36b6-2d85-48d6-a26c-88a57c613669,0219de4f-e72f-40e3-9aa7-547ca490803e…)]。已完成1个来源
```

关键观察：报错**只含 `PERMANENT_TOMBSTONES_DROPPED`，不含 `LOCAL_ACCOUNTS_DROPPED`/`REMOTE_ACCOUNTS_DROPPED`**。
`evaluateSyncSafety` 的「记录丢失」判定（missingIdentities）与「墓碑标记丢失」判定是分开的两条 reason。
只有墓碑 reason ⇒ 这 163 条记录**全都还存在于合并结果里**，只是 `isPermanentlyDeleted` 永久删除标记被丢掉。

## 2. 已用真实远端数据排除的假设

- **服务端「新账号」文件夹复活**（E 节原推断）：F 节只读 GET `or.sbbz.tech:5443`（revision 20）复核——
  服务端 194 账号（156 活跃 + 6 软删 + 32 永久墓碑）、10 文件夹（5 活跃 + 5 墓碑）。
  **服务端「新账号」文件夹是活跃的，并非墓碑** ⇒ 当前数据下 fixed-folder 分支不会触发，原推断不是当前触发点。
- **镜像 / WebDAV / 旧构建拦截**：用户 WebDAV 已取消勾选、服务器是唯一主源（merge 模式）、已重载到 1.8.5 ⇒ 均排除。
- **安全检查误报（纯 bug）**：用真实 bundle 端到端构造「本地 163 本地墓碑 + 32 服务端墓碑」两种时序，
  `reasons` 均为 `[]`，构造形态不复现 ⇒ 用户真实本地浏览器保险库形态与构造不同，尚未定位。

## 3. 主导假设

163 条 account 记录在合并结果里**标记被清除**（`unflagged`）：某条合并路径在收敛 account 时把
`isPermanentlyDeleted` 设成了 `false`。静态走查 `mergeSameAccount` / `mergeAccountCollections` /
`reconcileAccountFolders` / `syncAliasGroups` / `normalizeAccountShape` 都保留该标志，但真实本地数据形态
（如别名组、文件夹归属、recordId 大小写/规范化差异）尚未完全复现，故未坐实。

## 4. 1.8.6 判决性诊断增强

为让下一次点击一锤定音，把 `core/pass_core/js/sync_merge_core.js` 的
`PERMANENT_TOMBSTONES_DROPPED` 原因从「只给 ID+类型」升级为带诊断：

- 新增 `allIds(payload, kind)`（与 `tombstoneIds` 同形但不过滤标志），用于判定缺失的墓碑 ID 是否仍在 merged。
- 对每个类型（accounts/folders/passkeys）计算并输出：
  - `req`：本地 + 远端并集里的永久墓碑数（必须保留的）
  - `merged`：合并结果里仍为永久墓碑的数
  - `unflagged`：缺失里「记录在合并结果但标记被清除」的数（主导假设的判定信号）
  - `absent`：缺失里「记录本身消失」的数
  - `sample`：最多 4 个样本 ID + `mode`

新格式示例：

```
PERMANENT_TOMBSTONES_DROPPED[accounts:dropped=163(req=163,merged=0,unflagged=163,absent=0) sample=(id1,id2,id3,id4…); mode=merge]
```

判读：
- `unflagged=163 absent=0` ⇒ 坐实**合并逻辑清掉了 isPermanentlyDeleted**（合并 bug，下一步定位具体路径）。
- `absent=163` ⇒ 记录被合并**真删掉**。
- `unflagged=0` 且记录在 merged ⇒ **安全检查误报**（逻辑 bug），与上面两种都不同。

测试同步更新：`apps/extension_shared/tests/sync_merge.test.mjs` 用例 32 改为断言新格式
（含 `accounts:dropped=1` / `absent=1` / `unflagged=0` / `mode=merge`）；新增用例
「标记被清除计为 unflagged」覆盖主导假设（`unflagged=1 absent=0`）。

## 5. 用户下一步（必做，自动化无解）

Chrome 扩展「合并」按钮触发的主同步源指纹变更 `window.confirm` **既点不掉也绕不过**（见关联文档 D 节），
必须由用户在浏览器里手动操作：

1. 从 `apps/extension_chrome_web` **重新加载扩展**（Chrome 不会更新已开标签页的 content script，
   且重载扩展后须对目标页**硬刷新**；`pageVersion ≠ extensionVersion` 即说明没刷新到位）。
2. 点「合并」并**确认**主同步源变更弹窗。
3. 若仍被拦，**把中括号里整段**贴回来——尤其 `unflagged=` / `absent=` / `mode=`，即可定位 163 根因。

  （或重跑 `rotate_token.sh` 后在客户端同步更新）。已多次提醒，待用户处理。
- Chrome `dist/*.js` 的 `PASS_EXTENSION_VERSION` **不在 `version.mjs` 65 项校验覆盖内**（CI 缺口，H 节已记），
  本次靠手动「先 build 共享层再 build-extension-chrome-web.sh」规避；建议后续纳入校验。
