# 谷歌通行密钥无法注册进 Pass：attestation 要求不接管的实锤诊断

- 日期：2026-10-13 14:21
- 版本：1.9.3（用户实际加载的构建；诊断类问题，未改代码）
- 场景：myaccount.google.com「通行密钥和安全密钥」页，点「创建通行密钥」

## 用户实测日志（Console，一次拿全）

```
[Pass injected] create-intercepted
  {manageable: false, reason: 'attestation-required-by-rp',
   rpId: 'google.com', userName: 'ibjxk0@gmail.com', attachment: 'platform'}
[Pass injected] fallback-notice-posted
  {operation: 'create', reason: 'attestation-required-by-rp',
   message: 'Pass 未接管保存通行密钥，本次改由浏览器原生处理：网站要求可验证认证器证明'}
```

页面结果：Chrome 原生弹窗「保存通行密钥？」后出现过页面提示。

> ⚠️ 重要更正（2026-10-13 用户指正）：「确认完毕！现在，您可以使用您的指纹…」
> 这类文案是**谷歌账户页自带的固定提示**，与本次注册是否成功无关，**不能**用作
> 本次操作成功的证据。本诊断仅以 Console 日志为准。

## 结论

1. **被日志实锤的只有一件事**：Pass 因 `attestation-required-by-rp` 故意不接管
   谷歌的 create()，交给 Chrome 原生处理。**至于原生这条路最终有没有把密钥建
   起来，凭页面上的固定提示无法判断**——需看 Chrome 原生弹窗是否真的保存成功
   （iCloud 钥匙串是否新增条目）、谷歌是否报红字错误。
2. **Pass 不接管谷歌的 create() 是代码里的明确设计**（`webauthn_routing.js`
   `explainCreateManageability`）：谷歌的注册请求带可验证认证器要求
   （attestation direct/enterprise），Pass 是软件认证器，**没有经过 FIDO 认证的
   attestation 私钥和元数据链**，出具不了网站要求的认证器证明；硬接管只会被
   RP 拒绝。注释原话："Pass has no certified attestation key or metadata chain.
   Let Chrome use the real system authenticator when the RP explicitly requires
   proof."
3. 因此**谷歌的通行密钥永远注册不进 Pass**——这不是 bug，是安全模型的硬边界；
   同样地，任何不带认证链的软件密钥管理器都一样。黄色提示文字准确描述了原因，
   行为符合预期。
4. **~~若用户实际体验是「谷歌这一步整体失败、密钥没建起来」，那是 Chrome 原生
   路径的问题（与 Pass 无关），需另行排查原生报错~~ —— 这条已水落石出，见文末
   「最终根因实锤：InvalidStateError」一节。

## 判定方法（以后照抄）

谷歌页面 Console 搜 `create-intercepted`，看 `reason`：

| reason | 含义 | 结果 |
| --- | --- | --- |
| `attestation-required-by-rp` | 网站要求可验证认证器证明（谷歌即此） | 故意让位，密钥由 Chrome 原生处理（是否成功以原生弹窗为准） |
| `google-legacy-appid-request` | 谷歌旧式 AppID 外置密钥契约 | 故意让位 |
| `cross-platform-requested` | 网站要求外置安全密钥 | 故意让位 |
| `missing-challenge-or-user-id` | 请求参数不完整 | 让位 |
| `managed-by-pass`（manageable: true） | Pass 可接管 | 密钥进 Pass |

## 新增诊断：原生回退结果日志（2026-10-13 补）

为彻底搞清楚「Pass 让位后原生注册到底成功没」，给 `webauthn_injected.js` 的
`runFallbackCreate` / `runFallbackGet` 加了原生结果的记录：

- `create-fallback-native-success`：原生 create 返回了真实凭证（含 rpId、userName、
  credentialId 前 16 位、hasResponse）。
- `create-fallback-native-error`：原生 create 抛错（name/code/message）。
- `get-fallback-native-success` / `get-fallback-native-error`：get 对称日志。

复现后只需看这两条：有 `*-success` 即原生注册成功（密钥进了系统钥匙串）；
有 `*-error` 即原生侧失败、错误名即失败原因（如 `NotAllowedError`=用户取消或
系统认证器拒绝）。新增测试 `webauthn_fallback_logging.test.mjs` 用桩环境验证
两条分支都记录，200/200。

纯诊断，未改任何托管/让位决策逻辑；版本随 1.9.4→1.9.5。

- 同日早些时候的「读取通行密钥交给浏览器原生」是另一回事：那是登录/验证身份
  步骤（get），Pass 里没有 google.com 的存量密钥，自然交还浏览器 Touch ID。
- 扩展各层提示链路（injected → content → 页面 toast）本次实测工作正常，
  `deduped: false` 说明去重逻辑也未误伤。

## 最终根因实锤：InvalidStateError（原生拒绝重复注册）

用户复现后，原生回退日志给出了决定性证据（1.9.5 的埋点生效）：

```
VM549 webauthn_injected.js:207 [Pass injected] create-fallback-native-error
  {reason: 'attestation-required-by-rp', name: 'InvalidStateError',
   code: '11',
   message: 'The user attempted to register an authenticator that contains
             one of the credentials already registered with the relying party.'}
```
页面侧同时抛出未捕获的 `InvalidStateError: The user attempted to register an
authenticator that contains one of the credentials already registered with the
relying party.`

### 一锤定音的结论

1. **这是原生侧（系统平台认证器）的报错，不是 Pass，也不是同步。**
   - Pass 已因 `attestation-required-by-rp` 正确让位，日志里 `reason` 仍是这个值，
     说明让位链路工作正常；
   - 真正抛 `InvalidStateError` 的是 Chrome 把 create() 转交的**系统平台认证器**
     （本机即 iCloud 钥匙串 / Touch ID）。

2. **根因：同一个认证器上已存在该 RP 的凭据（不是账号注册数量限制）。**
   用户指出并截图实证：谷歌**不限制**注册数量——同一账号已有 5 枚通行密钥
   （iCloud 钥匙串 / 1Password / Google 密码管理工具 / Android note10 /
   Mac 上的 Chrome），分属五个**不同认证器**，跨认证器随便加。
   WebAuthn 规范限制的是**单个认证器**：RP 在 create() 请求里把已注册凭据 ID
   放进 `excludeCredentials`，认证器发现自己持有其中之一时**必须**返回
   `InvalidStateError`（code 11）。本次注册走的是本机 iCloud 钥匙串，而截图
   第一行「iCloud 钥匙串（2026-04-30 创建、上次使用 3 分钟前、Chrome/Mac）」
   正是该认证器持有的那枚 → 同一认证器重复创建被拒。

3. **为什么看起来像 Pass 的 bug。**
   黄色提示「Pass 未接管…交由浏览器原生处理」出现在最前，用户自然以为是 Pass 把
   注册搞没了。实际上 Pass 让位是**设计行为**（attestation 硬边界），让位后那段
   失败属于原生系统认证器，与 Pass 完全无关。

4. **如何解决 / 绕过。**
   - 最省事：直接用 iCloud 钥匙串里已有那枚登录，不需要再创建。
   - 想再添一枚：换一个**不同的认证器**创建即可（如 Android 上的 Google 密码
     管理工具、1Password、其他设备/浏览器）——跨认证器数量不限，不会报
     InvalidStateError。
   - 若一定要在 iCloud 钥匙串上重建：先在谷歌管理页删掉那枚 iCloud 钥匙串
     通行密钥，再回 Chrome 点「创建」。
   - 注意：无论哪种都进不了 Pass（attestation 硬边界，Pass 无 FIDO 认证证明链）。

5. **日志里的其他噪声与本次无关。**
   - `网站自动登录脚本.user.js ... TypeError`：用户自己的 Tampermonkey 用户脚本
     报错，与 Pass 无关。
   - `play.google.com/log ... ERR_BLOCKED_BY_CLIENT`：广告/请求拦截器拦了谷歌的
     日志上报，与 Pass 无关，也不影响注册结果。
   这两条都不改变「InvalidStateError = 设备已有谷歌通行密钥」的结论。

## 终局实验：让 Pass 接管谷歌注册 → 谷歌服务端拒绝（1.9.6→1.9.7 回滚）

为回答「怎么才能让 Google 用 Pass 而不是回退」，1.9.6（commit `dae38df1`）移除了
attestation 让位规则，让 Pass 直接接管谷歌注册。用户实测（v1.9.6，两次尝试）：

```
create-intercepted   {manageable: true, reason: 'managed-by-pass', rpId: 'google.com'}
create-bridge-success {createMode: 'replaced', credentialId: 'y7Jbi4fK…'}   // 第一次
create-bridge-success {createMode: 'replaced', credentialId: 'AmVNRkoV…'}   // 第二次
m=ws9Tlc,…:213 Uncaught (in promise) RpcError                            // 谷歌页面自身
```
页面弹窗：**「出了点问题：我们无法保存您所做的更改。请返回到您的账号设置，然后重试。」**

### 判读

1. **Pass 全链路成功**：接管（managed-by-pass）→ 桥接 → 后台生成凭据 → 返回页面，
   两次都拿到了真实 credentialId。扩展侧没有任何失败。
2. **谷歌服务端拒绝**：凭据交回后，谷歌自己的 RPC 报 `RpcError` 并弹「无法保存」。
   即谷歌强制校验 attestation，`fmt="none"` + 全零 AAGUID 的匿名证明**不被接受**。
3. **结论（最终版，实验级证据）**：谷歌的通行密钥**永远进不了 Pass**，这不是 Pass
   的缺陷，是谷歌服务端策略 + Pass 无 FIDO 认证链的叠加硬边界。任何无认证链的
   软件认证器（包括各种第三方密码管理器走自建凭据的路径）都会被同样拒绝。
4. **处置**：回滚 1.9.6 的让位移除，恢复 `attestation-required-by-rp` 让位
   （升 1.9.7）。让位后系统认证器（iCloud 钥匙串）是 attestation 型 RP 的唯一路径；
   同认证器已有一枚时的 `InvalidStateError` 见前文「最终根因实锤」。

### 遗留清理

1.9.6 两次实验在 Pass 里留下两枚**谷歌从未注册的孤儿凭据**
（credentialId 前缀 `y7Jbi4fK…`、`AmVNRkoV…`，rpId google.com），
可在 Pass 通行密钥列表里删除，不影响任何数据。

> 1.9.8 补充：桥接层已补 attestation 守卫（`direct`/`enterprise` 直接抛
> `PASSKEY_USE_BROWSER`），即使绕过注入脚本路由也不会产出不合规凭据。
