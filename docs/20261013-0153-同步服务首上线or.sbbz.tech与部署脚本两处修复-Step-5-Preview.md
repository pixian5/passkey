## 三、首次上线需要准备的东西（缺一不可）

1. **Bearer Token 文件** `/etc/pass-sync/tokens.conf`
   - 用仓库自带的脚本写（会校验 Token 不含逗号/空白，且不以明文回显）：
     ```bash
     PASS_SYNC_NEW_BEARER_TOKEN='<你的Token>' \
       /opt/pass-sync-source/apps/sync_server_ubuntu/rotate_token.sh /etc/pass-sync/tokens.conf default
     chown pass:pass /etc/pass-sync/tokens.conf && chmod 0600 /etc/pass-sync/tokens.conf
     ```
   - **`chown` 这一步不能省**：`rotate_token.sh` 以 root 建立 `0600`，而服务以 `pass` 用户运行，
     不改成 `pass:pass` 会因读不到文件而崩溃（服务端只校权限位不校属主，最容易漏）。
   - `load_config()` 要求该文件的权限位不得有 group/other 位（`mode & 0o077` 必须为 0）。

2. **监听地址** `/etc/pass-sync/pass-sync-server.env`
   - unit 里默认写的是 `PASS_SYNC_HOST=127.0.0.1`，**外部设备连不上**；对外提供服务必须显式监听全部地址：
     ```bash
     printf 'PASS_SYNC_HOST=0.0.0.0\nPASS_SYNC_PORT=5443\n' > /etc/pass-sync/pass-sync-server.env
     chmod 0600 /etc/pass-sync/pass-sync-server.env
     ```
   - `EnvironmentFile=-/etc/pass-sync/pass-sync-server.env` 位于 unit 中那批 `Environment=` **之后**，因此文件里的值会覆盖 unit 默认值。

3. **TLS 证书**：`deploy.sh` 会自动识别 `/etc/bz/certs/server.crt|server.key`，复制到 `/etc/pass-sync/tls/` 并把 `PASS_SYNC_TLS_CERT/KEY` 追加进 env。本次机器上已有 acme.sh 签发的通配证书：`CN=sbbz.tech`，SAN 为 `DNS:*.sbbz.tech, DNS:sbbz.tech`，有效期 `2026-10-08 → 2027-01-06`，可覆盖 `or.sbbz.tech`。

4. **GitHub Secrets**：`SYNC_SERVER_HOST` 必须是当前主机（`or.sbbz.tech` 或其真实 IP），`SYNC_SERVER_USER` / `SYNC_SERVER_SSH_KEY` 必须仍能登录。改法：`gh secret set SYNC_SERVER_HOST --repo pixian5/passkey --body "or.sbbz.tech"`。

以上第 1、2 项是**服务器本地配置**，不在仓库里，重装/换机需要重新做一遍。

## 四、部署脚本的两个缺陷（已修并提交 369ce5e7）

### 4.1 通配符证书必然导致健康检查失败

```bash
# 旧逻辑
health_host="$(openssl x509 -in "${tls_cert}" -noout -ext subjectAltName \
  | grep -oE 'DNS:[A-Za-z0-9.-]+' | head -n 1 | sed 's/^DNS://')"
```

`grep -oE 'DNS:[A-Za-z0-9.-]+'` 遇到 `DNS:*.sbbz.tech` 时，紧跟的字符 `*` 不在字符类里，**只能匹配到 `DNS:` 本身**，`sed` 之后得到空串 → 走到 hostname 校验分支 → `return 1` → 部署判定健康检查失败并回滚。也就是说，只要证书第一个 SAN 是通配项，部署必然失败。

修复：逐个读 SAN 条目，跳过含 `*` 的项，取第一个具体域名（`*.sbbz.tech, sbbz.tech` → `sbbz.tech`）。

### 4.2 上线后日志里的版本号永远是 unknown

`_read_service_version()` 原先只读 `Path(__file__).resolve().parents[2] / "VERSION"`（仓库根）。程序被 `install` 到 `/opt/pass-sync-server/` 后，`parents[2]` 是 `/`，读不到 `VERSION`，启动日志与 `/healthz` 都只能回报 `unknown`——恰好把上一轮刚加的版本埋点废掉。

修复：

- `_read_service_version()` 依次尝试 `PASS_SYNC_VERSION_FILE`（可选）→ 程序同级 `VERSION` → 上一级 → 上两级，命中即返回，全部缺失才 `unknown`
- `deploy.sh` 把仓库根 `VERSION` 安装到 `${INSTALL_DIR}/VERSION`，并把它加入 `managed_paths`（备份/回滚与程序绑定）

修复后的实机日志，版本号正常出现：

```
INFO pass_sync_server [Pass v1.8.4] pass-sync-server listening on 0.0.0.0:5443
     db=/var/lib/pass-sync/pass_sync.sqlite3 auth=enabled
```

## 五、排障陷阱：本机 Fake IP（TUN 模式）

开发机开着 TUN 的 Fake IP 模式时，`dig or.sbbz.tech`、甚至指定 `1.1.1.1 / 8.8.8.8 / 223.5.5.5` 都会返回 `198.18.1.93`（RFC 2544 保留段），据此判断「服务器不通」是**错判**。正确做法：

```bash
# 1) 绕过本机解析器拿真实 IP
curl -sS 'https://cloudflare-dns.com/dns-query?name=or.sbbz.tech&type=A' -H 'accept: application/dns-json'
# 2) 直连真实 IP 验证（不要依赖本机解析）
nc -z -G 8 18.225.117.121 5443
curl -sS --resolve "or.sbbz.tech:5443:18.225.117.121" https://or.sbbz.tech:5443/healthz
```

同理，GitHub Actions 这类 CI runner 的 SSH 目标取决于 Secrets 里的主机名，本机网络状况说明不了任何问题。

## 八、遗留建议

1. **Token 强度**：当前 Token 太短，等于对公网暴破敞口。建议换成 32 字节以上的随机串
   （自行生成后用 `rotate_token.sh` 写入），并同步更新所有客户端的同步设置。
2. **证书续期**：acme.sh 证书 2027-01-06 到期，`/etc/bz/certs` 是 `deploy.sh` 的来源，续期后需重跑一次部署才会同步到 `/etc/pass-sync/tls`。
3. **数据库是全新的**：旧节点若还有其他同步数据，迁移要另外做导入导出，不在本次范围内。
