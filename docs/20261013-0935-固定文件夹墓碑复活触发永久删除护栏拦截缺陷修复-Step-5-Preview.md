# 固定「新账号」文件夹墓碑被合并复活，触发 PERMANENT_TOMBSTONES_DROPPED 同步拦截

- 日期：2026-10-13
- 模型：Step-5-Preview
- 涉及版本：pass 1.8.4
- 影响端：Chrome 扩展（管理页 + 后台 Service Worker）、Firefox 扩展、Rust 合并权威（桌面 / 同步服务端写入）
- 状态：已修复、已加回归测试、已重建 Chrome `dist`、已通过 JS↔Rust 对拍

## 1. 现象

用户在 Chrome 扩展里点「合并」同步到 `or.sbbz.tech:5443` 自建服务器，回报错：

```
同步失败:Error:自建服务器[SAFETY_BLOCKED]:同步安全检查未通过:PERMANENT_TOMBSTONES_DROPPED(同步编号 09A24900)。已完成1个来源
```

关键现场：

- 扩展「同步设置」里 **WebDAV 镜像未勾选**，自建服务器是**唯一主源**（merge 模式）。
- 切换主源时弹过「主同步源与上次成功同步不一致」确认框（上次 `uk.sbbz.tech:53334` → 当前 `or.sbbz.tech:5443`），确认后继续正常路径。
- 多次重试（不同同步编号 51BAAC20 / 09A24900）**每次都失败** → 不是偶发冲突，是确定性死锁。

## 2. 排查结论（先排除的错误假设）

1. **不是镜像拦截**：WebDAV 没勾，服务器是唯一主源，merge 模式下主源推送不可能触发该护栏（已用生产函数 9 组场景复现验证，含 181 账号压力测试）。
2. **不是账号 / 通行密钥墓碑**：合并逻辑对账号、通行密钥的墓碑均正确保留，只有文件夹的「特例分支」会丢。
3. **不是旧构建**：仓库内 `dist/background.js` 与当前 `core/pass_core/js/sync_merge_core.js` 在 `mergeAccountCollections` / `evaluateSyncSafety` / 合并调用点上逐字节一致。

## 3. 根因

`mergeSameFolder` 对**内置「新账号」文件夹**（`FIXED_NEW_ACCOUNT_FOLDER_ID = f16a2c4e-4a2a-43d5-a670-3f1767d41001`）有一个特例分支：当**两侧都包含该文件夹**时，无论哪一侧是否标记为永久删除，合并结果都**强制写 `isPermanentlyDeleted: false`**（即「复活」）。

- JS：`core/pass_core/js/sync_merge_core.js` `mergeSameFolder`（原第 481-494 行）
- Rust：`core/pass_core/crates/merge/src/v2/merge.rs` `merge_same_folder`（原第 746-770 行，第 763-764 行 `is_deleted: false, is_permanently_deleted: false`）

而 `evaluateSyncSafety` 要求：合并结果必须保留本地 ∪ 远端中的**每一枚永久删除墓碑**，否则报 `PERMANENT_TOMBSTONES_DROPPED`。

### 数据是怎么走到这一步的

1. 桌面端（Rust 合并权威）某次把「新账号」文件夹**永久删除**并写入服务端 —— 当时服务端没有该文件夹（单边 → 墓碑被保留落盘），所以**服务端那份同步包里「新账号」文件夹是永久墓碑**。
2. 扩展本地从未删除它，仍是**活跃**状态。
3. 现在扩展合并「服务端墓碑 + 本地活跃」→ 两侧都有该文件夹 → 被特例分支强制复活为活跃 → 合并结果里不再有这枚墓碑。
4. 护栏发现 required（含服务端墓碑）中有 ID 不在 merged 中 → **必然拦截，每次都失败**。

确定性复现（`/tmp/repro_fixed_folder.mjs` 加载生产 `background.js` 真实函数）：

| 场景 | 结果 |
| --- | --- |
| 本地「新账号」墓碑 + 远端无 | reasons=[]（保留，正常） |
| **远端「新账号」墓碑 + 本地活跃** | **reasons=['PERMANENT_TOMBSTONES_DROPPED']（修复前）** |
| 普通文件夹墓碑（非 fixed） | reasons=[]（保留，正常） |
| 两侧均无 | reasons=[]（强制新建活跃，正常） |

只有「远端墓碑 + 本地活跃」这一种组合会触发，完全吻合用户现场。

## 4. 修复

让 fixed 文件夹分支与普通过滤文件夹分支**行为一致**——尊重已算好的 `keepPermanentlyDeleted` / `keepDeleted`，不再强制复活。

### JS（`core/pass_core/js/sync_merge_core.js` `mergeSameFolder` 的 fixed 分支）

```js
isDeleted: keepDeleted,
isPermanentlyDeleted: keepPermanentlyDeleted,
deletedAtMs: keepDeleted ? (latestDeletedAt || Math.max(leftUpdatedAt, rightUpdatedAt)) : null,
deletedDeviceName: keepDeleted ? (deletedDeviceName || DEFAULT_DEVICE_NAME) : "",
```

### Rust（`core/pass_core/crates/merge/src/v2/merge.rs` `merge_same_folder` 的 fixed 分支）

```rust
is_deleted: keep_permanently_deleted || keep_deleted,
is_permanently_deleted: keep_permanently_deleted,
deleted_at_ms: if keep_permanently_deleted || keep_deleted {
    Some(latest_deleted_at.max(left_updated_at.max(right_updated_at)))
} else { None },
deleted_device_name: if keep_permanently_deleted || keep_deleted {
    deleted_device_name.clone()
} else { String::new() },
```

> 注：`merge.rs` 第 914-933 行的「合并后固定文件夹后处理」本就 `preserve existing.is_permanently_deleted`，但因上游 `merge_same_folder` 强制 false，此前永远拿不到 true。修复后这条后处理与合并主体逻辑自洽。

修复后复现验证：F2 场景 `reasons=[]`，「新账号」文件夹墓碑被正确保留并双向扩散。

## 8. 遗留 / 注意

- 是否允许永久删除内置「新账号」默认文件夹，是产品语义问题；本修复只保证「合并不再死锁、尊重永久删除」，不禁止删除本身。如后续想禁止删除该文件夹，应在删除入口拦截，而非在合并里强制复活。
- Firefox / Safari 壳层共用同一份已重建 `dist`；本次未打包 Firefox XPI（避免副作用），其 `dist` 源码已是最新，重新走 `build-extension-firefox.sh` 即可生效。
- 同步失败报错仍是「盲报」（只给原因不给冲突 ID / 目标），定位耗时。后续可改进 `evaluateSyncSafety` 附带缺失墓碑 ID 与类型。
