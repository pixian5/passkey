# 版本号与日志埋点补齐（扩展 + 客户端）

> 版本：**1.8.4**
> 日期：2026-10-13
> 起因：1.8.2 / 1.8.3 排 WebAuthn PRF 问题时，最大的浪费发生在「不知道跑的是哪份代码」上——
> 扩展重载只重启 Service Worker，不会更新已打开标签页的 content script，导致新代码的注册能过、
> 获取却失败，来回几轮才定位。本文记录为此补齐的版本号显示 / 启动日志 / 版本不一致告警。

---

## 1. 为什么要做这件事

上一轮 Bitwarden 通行密钥解锁失败，根因不是代码 bug，而是**运行环境混跑了两份代码**：

| 上下文 | 重载扩展后是否更新 | 实际表现 |
| --- | --- | --- |
| Service Worker（background） | ✅ 立即重建 | 新逻辑生效 |
| content script（`document_start` / `document_idle`） | ❌ 不会重新注入 | 仍是旧版本 |
| 已打开的管理页 / 弹窗 | 视是否刷新而定 | 可能仍是旧版本 |

后果：PRF 注册（`extensions.prf = {}`，纯 JSON）走的新 SW 逻辑能成功，
而 PRF 获取依赖新加的 base64url 序列化——这段在 content script 里，没更新，于是失败。
**在日志里看不到版本，就只能靠猜。**

本次改动的目标：

1. 每个上下文**启动时都报自己的版本号**；
2. 每个界面**肉眼可见版本号**（弹窗、选项页、客户端标题栏）；
3. 页面侧与后台版本不一致时**主动告警**，直接给出「硬刷新标签页」的动作提示。

## 2. 版本来源

版本号仍然只有一处真源：仓库根目录 `VERSION`。
`node scripts/version.mjs check` 现在校验 **65 处**版本来源（本次新增 1 处）。

```bash
node scripts/version.mjs current   # 查看当前版本
node scripts/version.mjs bump      # 递增（1.8.3 → 1.8.4）
node scripts/version.mjs check     # 校验全部来源一致（含内嵌同步服务副本）
```

### 2.1 三个 JS 版本入口

| 文件 | 由谁生成 | 服务谁 |
| --- | --- | --- |
| `apps/extension_shared/extension_version.js` | `apps/extension_shared/scripts/build.mjs` 读 package.json | 扩展全部上下文（background / content / injected / popup / options） |
| `apps/codex-tauri/src/app_version.js` | `scripts/version.mjs` 读根 VERSION | 三端共用管理 UI（Tauri / Docker Web / Chrome web-options） |
| Rust `CARGO_PKG_VERSION` | `Cargo.toml` / `tauri.conf.json` | Tauri 壳、Docker Web 后端 |

`app_version.js` 同时被 `apps/codex-tauri/scripts/sync-web-ui.mjs` 复制到
`apps/extension_chrome_web/app_version.js`，所以 Chrome 的 web-options 页 Literal 不会漂移。

> 注意：改了 `pass_sync_server.py` 必须同步两处内嵌副本，否则 `version.mjs check` 会拒绝通过：
> `apps/codex-tauri/src-tauri/resources/pass_sync_server.py`
> `apps/app_macos/Resources/SyncServer/pass_sync_server.py`

## 3. 扩展侧埋点

### 3.1 启动日志（每个上下文各一行）

| 上下文 | 位置 | 日志样例 |
| --- | --- | --- |
| Service Worker | `background.js` | `[Pass v1.8.4] background ready {version:"1.8.4"}` |
| content script | `content.js`（原有） | `[Passkey Bridge] loaded {version, href}` |
| 页面注入脚本 | `webauthn_injected.js`（原有）+ DOM 属性 | `data-pass-injected-version="1.8.4"` |
| 弹窗 | `popup.js` 新增 | `[Pass v1.8.4] popup ready {version, runtimeId}` |
| 选项页 | `options.js` 新增 | `[Pass v1.8.4] options ready {version}` |

DOM 属性（排查时最省事的一手手段，控制台一行就能看）：

```js
document.documentElement.getAttribute("data-pass-injected-version"); // MAIN 世界注入脚本
document.documentElement.getAttribute("data-pass-content-version");  // isolated 世界 content script
```

### 3.2 界面可见版本号

- 弹窗底部右下角：`v1.8.4`（`popup.html` 新增 `#popupVersion`，`popup.css` 新增 `.popup-version`，可选中复制）
- 选项页底部右下角：`扩展版本 v1.8.4`（`options.html` 新增 `#optionsVersion`，`options.css` 新增 `.options-version`）

### 3.3 版本不一致告警（本次最有价值的一条）

链路：页面注入脚本 → window.postMessage → content script → Service Worker。

1. `webauthn_injected.js` 的 `postPageDiagnostic()` 现在带上 `pageVersion`（自己这份注入脚本的版本）；
2. `content.js` `forwardWebAuthnPageDiagnostic()` 带上 `pageVersion` 与 `contentVersion`，
   两者不一致时在**页面控制台**打 `console.warn`「版本不一致…请硬刷新（Cmd/Ctrl+Shift+R）」；
3. `background.js` `recordPasskeyPageDiagnostic()` 比较 `pageVersion` 与 `PASS_EXTENSION_VERSION`，
   不一致时在 **Service Worker 控制台**打 `version-mismatch {surface:"page-vs-background", ...}`，
   并同时写入注册诊断时间线（选项页「复制注册诊断」可直接导出）。

```jsonc
// 诊断时间线里的新增字段
{
  "extensionVersion": "1.8.4",   // Service Worker 版本
  "pageVersion": "1.8.3",         // 页面注入脚本版本 ← 出现差异即为内容脚本没更新
  "phase": "page-api-called"
}
```

**看到 pageVersion ≠ extensionVersion，第一动作就是 `Cmd/Ctrl+Shift+R` 硬刷新目标标签页。**

## 4. 客户端侧埋点

### 4.1 Tauri 桌面客户端

- `apps/codex-tauri/src-tauri/src/main.rs`：`setup()` 首行打印
  `[Pass v1.8.4] tauri setup`（`println!`，终端 / 控制台可见）
- 共用管理 UI `apps/codex-tauri/src/main.js`：
  - 引入 `APP_VERSION`，`LOG_PREFIX = "[Pass v<版本>]"`
  - `boot` / `surface-ready` 两条日志带 `version` 与 `surface`（`tauri` / `web` / `extension`）
  - 标题栏 `.app-title` 与 `document.title` 写为 `Pass v1.8.4`

### 4.2 Docker Web（Rust）

- `apps/pass-web/src/main.rs`：
  - 配置校验通过后立刻打印
    `[Pass v1.8.4] pass-web starting: data_dir=… static_dir=…`（即使后续 vault 打开失败也留痕）
  - 监听成功后打印 `[Pass v1.8.4] pass-web ready: http://host:port`
- `/healthz` 已内含 `version`（`CARGO_PKG_VERSION`），容器里 `curl /healthz` 即可确认线上版本

### 4.3 同步服务（顺手补的排障信息）

`apps/sync_server_ubuntu/pass_sync_server.py`：

- 新增 `_read_service_version()`：从仓库根 `VERSION` 读版本号，读不到退回 `unknown`
- 启动日志：`[Pass v1.8.4] pass-sync-server listening on host:port db=… auth=…`
- `/healthz` 响应新增 `version` 字段

> 同步服务不是三端管理面之一，加它纯粹因为「服务器上跑的是哪份」同样是高频疑问。
> 改动只增字段、不改行为，现有 healthz 断言（`payload["ok"]`）不受影响。

## 5. 排障口诀

```
1. 看界面右下角 / 标题栏的版本号和 git 版本对不对得上
2. 扩展排障先看 Service Worker 控制台的 background ready
3. 页面侧看 data-pass-injected-version / data-pass-content-version
4. 出现 pageVersion ≠ extensionVersion → 硬刷新标签页（重载扩展不算）
5. 客户端看启动第一行 stdout；Docker Web / 同步服务看容器日志 + /healthz 的 version
```
