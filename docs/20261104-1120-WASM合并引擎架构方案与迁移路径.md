# WASM 合并引擎架构方案与迁移路径设计

> 状态：**技术预研与架构定案**（版本 2.0.3+ 演进方向）  
> 目标：消除 Chrome 扩展中 1,077 行 JS 合并实现（`sync_merge_core.js`），彻底终结 JS ↔ Rust 双轨维护税与黄金向量对拍负担。

---

## 一、 现状与痛点量化

当前跨端合并实现采用双轨制：
- **Rust `pass_merge::v2`**：3,809 行（作为唯一业务权威，服务于 Tauri 桌面与 Docker Web）；
- **JS `sync_merge_core.js`**：1,077 行（服务于 Chrome MV3 扩展与扩展共享层）；
- **对拍守卫 `check_merge_parity.mjs`**：48 项确定性属性测试，比对两个实现的输出一致性。

### 核心痛点：
1. **双重修改开销**：任何时间戳决胜逻辑、域名别名合并、或者墓碑处理规则的变动，必须用两种语言分别实现一套；
2. **边缘行为差异风险**：JavaScript 的 Number 精度（53-bit）与 Rust `i64` 时间戳、以及正则引擎（ECMAScript vs Rust `regex`）存在细微边界差异；
3. **测试维护负担**：任何语义调整必须先改 Rust -> 更新黄金向量 -> 调通 JS 对拍。

---

## 二、 `pass-merge` 的 WASM 编译可行性分析

经对 `core/pass_core/crates/merge` 源码与依赖树审计：
- **依赖纯净度**：仅依赖 `pass-domain`、`serde`（derive）与 `serde_json`；
- **零系统调用**：无操作系统原生依赖（无 `tokio`、无 `rusqlite`、无 `fs`、无网络套接字）；
- **计算纯度**：属于纯内存数据变换与 CRDT LWW 计算模型。

结论：`pass-merge` 具备 **100% `wasm32-unknown-unknown` 零改造编译条件**。

---

## 三、 WASM 接口契约设计（轻量 ABI）

为了在 MV3 扩展 Service Worker 中快速加载，不引入庞大的 `wasm-bindgen` 运行时绑定胶水代码，采用精简的 C-style 线性内存导出接口：

```rust
// core/pass_core/crates/merge/src/wasm.rs（设计模型）

#[no_mangle]
pub extern "C" fn pass_wasm_alloc(size: usize) -> *mut u8 {
    let mut buf = Vec::with_capacity(size);
    let ptr = buf.as_mut_ptr();
    std::mem::forget(buf);
    ptr
}

#[no_mangle]
pub unsafe extern "C" fn pass_wasm_dealloc(ptr: *mut u8, size: usize) {
    if !ptr.is_null() && size > 0 {
        drop(Vec::from_raw_parts(ptr, 0, size));
    }
}

#[no_mangle]
pub unsafe extern "C" fn pass_wasm_merge_payloads(
    local_ptr: *const u8, local_len: usize,
    remote_ptr: *const u8, remote_len: usize,
    mode_ptr: *const u8, mode_len: usize,
    device_ptr: *const u8, device_len: usize,
    out_len_ptr: *mut usize,
) -> *mut u8 {
    // 读取输入切片并调用 pass_merge::v2::merge_payloads
    // 序列化为 JSON 写入线性内存，返回缓冲区指针与长度
}
```

### 内存开销与体积预估
- `pass-merge` release WASM 产物预估体积：**~120KB - 160KB**（开启 `opt-level = 'z'` 与 `lto = true` 后）；
- Gzip 压缩后体积：**< 45KB**；
- 扩展 Service Worker 首次冷启动编译耗时：**< 3ms**。

## 四、 Chrome MV3 适配与渐进式平滑迁移计划

### 1. MV3 Service Worker 安全策略
Chrome MV3 规定扩展 Service Worker 必须加载本地打包的 WASM（禁止从网络动态 `eval`），满足本地离线与安全合规约束：
```javascript
const wasmModule = await WebAssembly.instantiateStreaming(
  fetch(chrome.runtime.getURL('dist/pass_merge.wasm'))
);
```

### 2. 三阶段落地路径：
- **阶段 1（同轨影子运行）**：
  在扩展共享层引入编译好的 `pass_merge.wasm`，在 `sync_background` 执行合并时同时运行 JS 与 WASM，校验二者输出（如有不符上报告警并回退至原有逻辑）；
- **阶段 2（默认切换为 WASM）**：
  将扩展默认合并引擎切换为 WASM；原有 JS 合并实现标记为 `@deprecated`；
- **阶段 3（代码库减负）**：
  彻底移除 `apps/extension_shared/` 中的 `sync_merge_core.js`（削减 1,077 行冗余代码）；`check_merge_parity.mjs` 转换为 WASM 与 Rust 本地二进制的冒烟对拍。
