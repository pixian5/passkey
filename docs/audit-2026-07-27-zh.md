# 同步功能复核记录（2026-07-27）

本轮复核覆盖扩展选项页、扩展后台自动同步、Tauri 自建服务器/WebDAV、Docker Web，以及共享 JS/Rust 合并核心。

## 已确认并修复

### 本轮追加修复（2026-07-27）

- Docker Web 的联网同步 worker 只在内存副本上运行；`Vault.save()` 在 worker 阶段被延迟，最终由持有 vault 锁的线程执行完整 payload CAS 后才落盘。联网期间的本地编辑会使 CAS 失败，不会被网络结果覆盖。
- Tauri 同步回调使用 SQLite 事务内的“读取当前 payload→比较期望值→写入全部集合”原子 CAS；账号、文件夹、通行密钥及两组顶层排序不会在检查与提交之间被并发编辑插入。
- Swift、扩展选项页和扩展后台在主同步源推送失败后不再继续写入镜像；镜像会显示跳过原因，失败目标仍进入 outbox。
- Swift `AccountFolder` 已包含 `regularAccountIds`、`regularOrderUpdatedAtMs`、`regularOrderUpdatedDeviceName`，并在 Codable、合并及新加入文件夹路径中保留/更新该字段；文件夹视图优先使用该数组排序。
- Swift 同步包导入现在先解密、合并、安全检查并弹出账号差异预览；确认后重新校验本地 payload、创建安全快照，再执行写入，取消或确认期间本地变化均不会写入。
- Chrome Web 恢复快照现在强制 HTTPS（回环地址例外）、30 秒请求超时、`Idempotency-Key` 和完整恢复回执校验；普通自建服务器 PUT 同样校验提交回执。
- Swift WebDAV 首次写入无 ETag 时发送 `If-None-Match: *`；所有端的冲突重试在重新合并前重新读取并比较本地 payload，发现本地编辑立即停止。
- Tauri 同步、WebDAV、同步包导入和服务器快照恢复均写入撤销历史，恢复前仍保留安全快照；冲突重试次数统一为 5 次。

### 1. 多来源同步的主源边界

- `syncPrimarySource` 指定的来源是唯一合并输入。
- 其它已启用来源是镜像目标，只接收最终本地结果，不参与账号、文件夹、通行密钥或排序数组的裁决。
- 所有来源仍会先拉取并记录 ETag；主源拉取失败会停止本次同步，避免用不完整数据覆盖镜像。
- 镜像拉取失败不会阻塞主源：记录为本次部分失败并进入后续补偿；主源失败仍立即停止。
- 主源成功、镜像推送失败时，本地结果仍保留，并为失败镜像创建 outbox 补偿任务。
- 主源返回真正的空同步包时仍经过安全闸门；404/无文件表示首次初始化，可将本地数据推送到远端。

### 2. 永久删除墓碑与安全统计

- 永久删除账号、文件夹、通行密钥墓碑不计入“可见数据”数量。
- 墓碑的稳定 ID 仍计入身份集合，合并时不会被旧设备的活动记录复活。
- 只有墓碑的本地数据面对空远端可以安全同步；普通可见数据面对空远端仍会阻止写入。
- JS 与 Rust 安全统计、身份保护和对拍测试保持一致。

### 3. 条件写入与冲突重试

- 自建服务器的 HTTP 412、428 均统一为 `PRECONDITION_FAILED`，进入拉取、合并、重试流程。
- WebDAV 有 ETag 时使用 `If-Match`，无 ETag 时使用 `If-None-Match: *`，避免首次写入覆盖已有文件。
- Tauri 一次逻辑同步生成一个幂等键，冲突重试复用同一键；自建服务器因此可以识别网络响应丢失后的重放。
- 扩展端 merge/云端覆盖重试也复用同一幂等键，并识别 412/428。
- WebDAV 没有统一的幂等协议，Tauri/WebDAV 传输层会忽略该键；仍依靠 ETag 条件写入。
- 本地写入发生后再推送失败，报告 `applied: true, pushed: false`，并保留本地结果供下一次同步或 outbox 补偿。
- 自建服务器成功写入必须返回并校验 JSON 回执：`ok`、`committed`、`scope`、`etag`、`payloadSha256`、`revision`、`idempotencyKey`；这些字段还要分别与 `ETag`、`X-Sync-Scope`、`X-Payload-Sha256`、`X-Sync-Revision`、`X-Sync-Idempotency-Key` 响应头一致。
- 服务器快照恢复同样必须带 `Idempotency-Key`，服务端按 scope/key 重放，不重复创建版本；客户端会校验恢复回执后才刷新本地。
- `X-Sync-Revision` 是 scope 内连续 revision，不再使用全局 `version_id` 直接充当 revision；旧数据库启动时会为历史版本补齐 scope revision。

### 4. 合并前安全边界

- 站点别名归并会改变站点关系及其活动时间，必须在安全闸门之前对本地、主源和合并候选统一执行。
- 别名归并不能绕过永久删除墓碑；安全检查通过后才允许写本地或推送远端。
- `pinnedViews` 按作用域键合并：双方都有同一作用域时由较新的账号裁决，一方独有作用域保留。

### 5. 密钥轮换与空密钥模式

- 当前同步加密密钥为空时仍允许明文同步包；配置非空密钥时拒绝明文包。
- 配置新密钥后，预览、执行同步、WebDAV、自建服务器、服务器快照恢复和同步包导入都可使用运行时的 `previousEncryptionKey` 回退读取旧包。
- 加密信封的 `keyId` 必须匹配候选密钥；错误密钥不会因解密尝试而被接受。
- 回退密钥仅运行时使用，不写入 `SyncSettings` 的持久化 JSON。

### 6. 扩展跨上下文互斥

- 选项页和后台 Service Worker 各自保留内存 in-flight 标志。
- 同步开始时还会申请 `chrome.storage.session` 短时锁，锁带 10 分钟过期时间，异常退出不会永久阻塞。
- 没有 `storage.session` 的旧环境退回当前上下文锁；该降级不影响单上下文互斥。

## 迁移与兼容策略

同步服务器本轮新增 `scope_revision`，它是每个同步 scope 内连续递增的协议 revision；旧数据库可能没有该列，或只在部分表存在。服务启动时在同一初始化事务中执行以下迁移：

1. 为 `payload_versions`、`sync_idempotency` 和 `payloads` 缺失的 `scope_revision` 列执行 `ALTER TABLE`；已有数据不删除、不重写载荷正文。
2. 按 `scope`、`version_id` 升序检查历史 `payload_versions`；完整且全部为正数的 scope 保持原值，某个 scope 只要存在缺失/非法 revision，就按该 scope 全量重建从 1 开始的连续 revision。
3. 按 `scope + etag` 从版本表回填当前 `payloads.scope_revision`；找不到对应历史版本时保留 0，下一次成功写入从当前 scope 最大 revision 加 1 开始。
4. 按 `scope + etag` 回填幂等表的 revision；找不到匹配版本时保留 0，幂等重放仍返回原有 ETag/载荷摘要，不凭空创建新版本。
5. 后续 PUT/restore 每次只追加一条新的 `payload_versions`，并在同一事务写入当前 payload、幂等记录和 scope revision；跨 scope 写入不会改变其它 scope 的 revision。

`scope_revision` 迁移本身只增加/回填元数据列，不重写载荷 JSON，也不生成 Bearer Token、同步加密密钥或新的业务数据。启动阶段另有既存的协议兼容清理：不支持的旧 payload 会被移入临时 `.jsonl` 记录后从当前表移除；这不是 revision 回填的一部分。升级前仍应备份 SQLite 文件；回滚到不认识该列的旧服务器前必须恢复备份，不能让新旧进程同时写同一个数据库。

## 当前同步写入顺序

1. 读取本地完整 payload（账号、通行密钥、文件夹、全局排序、文件夹排序及更新时间）。
2. 拉取所有启用来源；主源失败立即停止，镜像失败记录并继续。
3. 对本地和主源执行别名归并，再仅使用主源 payload 与本地数据按字段时间戳、设备名和关系墓碑合并。
4. 再次规范化别名与 `pinnedViews`，执行永久删除墓碑安全检查和实体身份完整性检查。
5. 保存本地安全快照。
6. 写入本地合并结果。
7. 按主源优先顺序推送主源和镜像目标，使用 ETag/幂等键条件写入；主源推送失败时停止后续镜像写入，避免镜像之间出现分叉。
8. 实际失败目标进入 outbox；被主源失败主动跳过的镜像只记录“已跳过”状态，待下一轮主源成功后再写入。

## 仍需明确的边界

- WebDAV 服务端若不返回 ETag，客户端只能使用首次写入保护（`If-None-Match: *`），无法对已有文件做可靠的并发检测；应优先使用支持 ETag 的 WebDAV 服务。
- `storage.session` 锁的写入与校验不是跨进程事务锁，极短时间内两个上下文同时首次申请仍可能竞争；真正的最终一致性由远端 ETag/428 和本地 outbox 保护。
- 主源选择是客户端设置，不是远端服务端概念；不同设备应使用相同主源设置，避免把两个镜像互相当成权威源。
