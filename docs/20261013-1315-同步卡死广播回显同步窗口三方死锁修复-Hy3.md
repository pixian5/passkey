# 同步"正在同步…"卡死：广播-回显-同步窗口三方死锁修复

- 日期：2026-10-13 13:15
- 版本：1.9.2 → 1.9.3
- 影响端：Chrome 扩展（其他复用 `extension_shared/background.js` 的端同样受益）

## 现象

1.9.2 发布后，用户在管理页点同步按钮，「正在同步…」转圈永久不结束（截图
`PixPin_2026-10-13_13-12-13.png`），无报错、无超时。

## 根因：三方死锁

1.9.2 引入的**同步窗口写闸门**（`handleWebBridgeSyncData` 落库前
`await waitSyncWindowEnd()`）与既有的广播/回显链路构成环：

```
同步流程（窗口开着）
  └─ await broadcastWebBridgeData(next)        # 等页面 ack
       └─ 页面 extension-bridge 收到广播
            └─ persist(store)
                 └─ await syncWebBridgeData(...)   # 回发 PASS_WEB_BRIDGE_SYNC_DATA，等后台响应
                      └─ handleWebBridgeSyncData
                           └─ await waitSyncWindowEnd()   # 等同步结束才关窗
                                └─ 同步在等广播 ack，环闭合 → 永久互等
```

三环：同步 → 广播 ack → 页面 persist → 回显响应 → 窗口结束 → 同步。
任何一方不先让步，全部挂起。

## 修复（1.9.3）

**广播即发即忘**（`background.js` `broadcastWebBridgeData`）：不再 `await`
`chrome.runtime.sendMessage` 的页面 ack，只挂一个 `.catch` 吞掉"页面未开"的
正常报错。环从"同步不再等页面"处断开：

- 同步继续执行 → 收尾关窗 → 挂起的回显被唤醒 → 等值守卫跳过等价回显（或推迟
  落库真实编辑）→ 一切收敛。
- 页面 persist 行为不变；回显闸门（1.9.2 的核心防误报机制）完整保留。

## 教训

引入"等待某条件"的闸门时，必须排查所有进入该等待路径的调用方是否可能自身
处于被等待链上（await 消息 ack 是最典型的隐藏环）。事件循环单线程不等于
无死锁——跨上下文消息通道 + Promise 互等同样会锁死。
