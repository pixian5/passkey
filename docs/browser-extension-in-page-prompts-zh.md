# 浏览器扩展网页内浮窗交互

> 状态：当前实现（版本 1.6.9；完成本轮全项目文档同步后随仓库版本递增）。本文只描述 `apps/extension_shared/content.js` 注入登录页后的账号选择和保存/更新确认交互；Chrome 管理页、工具栏 popup 与 WebAuthn 的完整协议不在本文范围。

## 1. 目标与边界

Chrome 自带的密码选择框、网站自己的定位/堆叠上下文和全局 CSS 都可能遮挡或破坏扩展的网页内界面。Pass 的网页内浮窗因此必须：

- 位于浏览器视口右上角，优先进入 Popover top layer；
- 不继承网站的 CSS，也不把账号、密码等敏感内容暴露给页面脚本；
- 允许用户把账号选择框和保存/更新确认框拖离 Chrome 原生密码选择框；
- 保存密码前必须由用户明确决定，不能再用阻塞浏览器的 `window.confirm`；
- 任何保存提示都不得展示密码正文。

这些规则只处理当前页面的 UI。它们不改变网站表单、Chrome 原生密码管理器或后台账号存储的权限边界。

## 2. 实现位置与构建产物

| 职责 | 源文件 | 运行产物 |
| --- | --- | --- |
| 网页内账号选择、保存/更新提示、提交拦截 | `apps/extension_shared/content.js` | `apps/extension_chrome_web/dist/content.js` |
| 可拖动浮层与视口边界约束 | `apps/extension_shared/floating_drag.js` | 随 content script 打包 |
| Chrome 保存/更新判断与写入 | `apps/extension_shared/background.js` | `apps/extension_chrome_web/dist/background.js` |
| 浮窗和拖拽回归 | `apps/extension_shared/tests/content_toast_contract.test.mjs`、`apps/extension_shared/tests/floating_drag.test.mjs` | `npm test` |

修改共享源码后，必须依次执行：

```bash
cd apps/extension_shared
npm test
npm run build
cd ../..
./scripts/build-extension-chrome-web.sh
```

`apps/extension_shared/dist/` 是临时共享构建目录，不提交；正式 Chrome 扩展加载 `apps/extension_chrome_web/dist/` 中已跟踪的生成文件。

## 3. 浮窗通用约束

所有此处定义的网页内浮窗由 content script 创建宿主元素，挂接 closed Shadow DOM，再写入最小且带 `!important` 的关键定位样式。这样页面无法通过选择器读取 Shadow DOM 内的账号按钮或确认按钮，也不能依赖全局 `font-size`、`transform`、`position` 等规则破坏布局。

## 3.1 提交恢复与页面重渲染

拦截登录表单后，页面可能在等待用户决定期间重新渲染并替换或移除原表单。恢复提交前必须同时确认原表单仍为 `HTMLFormElement` 且 `isConnected`，提交按钮仍连接到文档并且 `submitter.form === form`；否则直接放弃恢复，不向页面抛出 Chrome 的“Form submission canceled because the form is not connected”错误。恢复调用使用 `HTMLFormElement.prototype.submit.call(form)` 作为无提交按钮或竞态失败时的兜底，避免页面中的 `name="submit"` 字段覆盖原生方法。

宿主优先使用 `popover="manual"` 和 `showPopover()` 进入浏览器 top layer；浏览器不支持时保留 `position: fixed` 回退。初始位置均为距右上角 14px，最大宽度为 `min(360px, calc(100vw - 28px))`。

同一页面并行安装多个 Pass 版本时，内容脚本以三段版本号决定账号选择和 toast 的 UI 所有权；新版本会移除旧版本的这两类界面，同版本才以扩展 ID 打破平局。已经打开的保存/更新确认仍归发起提交拦截的内容脚本处理，必须通过该浮窗的明确按钮结束，不能假定新版本会替旧上下文自动提交或自动取消。

## 4. 拖动规则

账号选择框和保存/更新确认框共用 `installFloatingDrag`：

1. 只有鼠标/触控笔主指针从标题栏或浮窗外层留白区域按下时才开始拖动。
2. 账号按钮、确认按钮、关闭按钮、输入控件、链接和可滚动列表带有“不可拖动”标记，保持原有点击和滚动行为。
3. 移动期间使用 Pointer Capture，指针移出浮窗仍可连续拖动。
4. 位置在每次移动时钳制在可视区域内，四周至少保留 8px；浮窗大于视口时固定在安全边距。
5. 用户再次打开浮窗时回到默认右上角位置；位置不写入网页、扩展存储或同步数据。

这个设计的目的是让用户在 Chrome 原生密码选择框覆盖时自行移动 Pass 浮窗，而不是尝试覆盖或控制 Chrome 自带界面。

## 5. 账号选择流程

当用户名或密码输入框获得用户明确激活时，content script 向后台请求当前站点的候选账号元数据。列表响应不包含密码；只有用户点击某个账号后，后台才返回该账号的用户名和密码给隔离世界中的 content script 填充。

一次鼠标点击通常同时触发 `pointerdown`、`focusin` 和 `click`。内容脚本以输入框对象和 650ms 窗口认领一次激活，避免三个事件分别发起列表请求或创建多个选择框。窗口滚动、窗口尺寸变化、点击浮窗之外或成功填充都会关闭账号选择框。

用户名输入框产生用户输入后，账号选择列表在本地按用户名做大小写不敏感的子串筛选；例如输入 `alice` 会同时匹配 `Alice@example.com` 和 `alice.work`。空输入恢复完整候选列表。筛选不向后台重复请求，也不读取或显示密码；没有匹配时浮窗保留打开并显示“没有匹配的账号”，方便用户继续编辑用户名。

## 6. 保存与更新密码流程

网站表单提交后，content script 从当前表单提取域名、用户名和非空密码，并先向后台发送 `PASS_CONTENT_CHECK_LOGIN`。后台按当前标签页域名、账号站点和用户名判断：

| 后台结果 | 浮窗 | 用户操作 |
| --- | --- | --- |
| 同站点、同用户名、同密码已存在 | 不显示浮窗 | 立即继续提交 |
| 同站点、同用户名、密码不同 | “检测到该账号密码已更改”“更新已保存的密码？” | “更新并继续”写回新密码；“暂不保存”只继续提交 |
| 没有同用户名的匹配账号 | “检测到一个尚未保存的登录账号”“保存这个账号？” | “保存并继续”创建账号；“暂不保存”只继续提交 |

显示保存/更新浮窗时，原表单提交会保持拦截状态。浮窗没有自动关闭计时器；用户不点击“更新并继续”“保存并继续”或“暂不保存”时，提示与提交状态都会保留。再次提交同一页面表单也会继续被拦截，不能绕过确认浮窗。

只有后台在 800ms 内完全没有回应时，内容脚本才会放行原始提交，避免扩展上下文失效把用户永久卡在登录页。一旦后台已响应并显示浮窗，800ms 兜底不会再生效。用户选择保存或更新后，content script 才发送 `PASS_SAVE_FROM_LOGIN`，然后恢复原始提交；用户选择暂不保存则直接恢复原始提交。

## 7. 安全与隐私要求

- 不在账号选择列表、保存/更新浮窗、toast、控制台或测试断言中显示密码。
- `PASS_CONTENT_CHECK_LOGIN` 的职责仅是判断是否提示；列表接口同样不能返回密码。
- `PASS_SAVE_FROM_LOGIN` 只在用户点击保存/更新按钮后发送。
- 所有按钮拒绝 `isTrusted === false` 的合成点击，降低页面脚本借由事件重定向触发保存的风险。
- 跨扩展上下文不能直接调用另一个内容脚本的提交回调。若页面在保存/更新确认未决时重载扩展或并行加载新版本，用户必须通过当前可见确认按钮完成决定，或刷新页面后重新提交；不得把这一过程描述为已经自动保存、自动更新或已恢复旧提交。

## 8. 手工验收

1. 在 Chrome 的 `chrome://extensions` 重新加载 `apps/extension_chrome_web`。
2. 使用已有匹配账号打开登录页，点击用户名或密码框，确认账号选择框出现。
3. 在用户名框输入候选用户名的一部分，确认列表只显示包含该片段的账号，大小写不同仍能匹配。
4. 清空用户名框，确认完整候选列表恢复；输入不存在的片段，确认浮窗显示“没有匹配的账号”且仍可继续编辑。
5. 按住账号选择框标题或外层留白，把它拖到左下方；确认账号按钮仍可点击，列表仍可滚动，浮窗不能拖出屏幕。
6. 用已有账号但改过密码提交登录表单；确认显示“更新已保存的密码？”，且停留超过 800ms 仍不消失。
7. 点击“暂不保存”，确认网站继续登录且已有密码未改变。
8. 再次提交并点击“更新并继续”，确认网站继续登录且扩展中密码更新。
9. 使用新用户名提交，确认文案改为“保存这个账号？”和“保存并继续”。
10. 在浮窗存在时按回车或再次点击网站提交按钮，确认浮窗仍保留且页面不导航；只点击浮窗内按钮后才继续。

本地测试页可由以下命令启动：

```bash
python3 -m http.server 8766 --bind 127.0.0.1
```

然后访问 `http://127.0.0.1:8766/scripts/fixtures/extension-autofill.html`。`extension-toast-hostile.html` 用于验证网页恶意 CSS 不会改变浮窗的定位和字体。

## 9. 故障排查

| 现象 | 检查顺序 |
| --- | --- |
| Chrome 仍显示旧的浏览器确认框 | 在扩展页重新加载扩展，并确认加载目录是 `apps/extension_chrome_web`；检查 `dist/content.js` 是否随构建刷新。 |
| 浮窗不显示 | 确认扩展已解锁、表单包含可见的用户名和非空密码、当前页面为 HTTPS 或本机 HTTP；再检查当前站点是否已有完全相同的账号。 |
| 密码变化却显示保存而非更新 | 确认存量账号的站点能够匹配当前域名，且用户名完全相同；域名、别名组和用户名是更新判断的必要条件。 |
| 浮窗被遮挡或样式异常 | 确认宿主使用 closed Shadow DOM 和 manual Popover；在不支持 Popover 的浏览器检查 fixed 回退是否仍带关键 `!important` 定位。 |
| 无法继续登录 | 查看扩展后台是否能响应 `PASS_CONTENT_CHECK_LOGIN`；只有该请求完全无响应时才应在 800ms 后放行。若浮窗存在，必须通过其按钮完成本次决定。 |
